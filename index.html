01 / ObjectTracer

ObjectTracer.

One world.
Why so many maps?

I’ve always wondered what’s happening beyond what I can see. Aircraft above us. Ships between continents. Satellites overhead. Following them meant switching between separate worlds.

So I built ObjectTracer: one explorable globe. From the backend and real-time streams to the interface and 3D rendering, I kept building until those signals felt connected.

02 / Streaming
The whole picture first.
Only the changes after.

A snapshot establishes the view. Delta messages update the objects that moved or disappeared. When the visitor pans or zooms, the viewport tells the server which part of the world matters.

Snapshot to deltas · viewport bounds · WebSocket hub
03 / Reliability
The invisible work
behind a fluid experience.

Reconnect handling, stale-object cleanup, bounded tile loading, and mobile memory fixes keep the experience usable beyond the ideal demo. Those decisions are part of the product, too.

Connection lifecycle · memory limits · progressive tiles

The challenge

Different data sources, refresh rates, and spatial scales have to feel like a single continuous experience. Rendering and network traffic both need to stay responsive.

What I built

A Go backend with independent data-source workers, Redis for live state, PostgreSQL for trails, and viewport-filtered WebSocket updates. React and Three.js translate those streams into an explorable world.

Beyond the code

I own the product from architecture and development through deployment, monitoring, analytics, search optimization, and continuous delivery on Railway and Vercel.

Inside SEBIRA / Architectural intent becomes an executable system

A line in a drawing.
A chain of reasons behind it.

A language model can suggest a dimension. An architectural system has to explain it, validate it, and keep that explanation attached as it becomes geometry.

  1. 01 / Ingestion
    Read with provenance.

    Record the source, licence, jurisdiction, and passage.

  2. 02 / Knowledge
    Connect the evidence.

    Build concepts and relations with evidence attached to each edge.

  3. 03 / Brief
    Understand the intent.

    Translate the request into a typed brief and surface what is missing.

  4. 04 / Decision
    Check the claim.

    Verify quotations and jurisdiction before accepting a candidate value.

  5. 05 / Operations
    Make it executable.

    Compose supported operations with cited dimensions.

  6. 06 / Geometry
    Let the kernel decide.

    Solve wall networks and execute geometry in Rust.

  7. 07 / Drawing
    Measure what was built.

    Derive dimensioned plans and sections from the geometry.

  8. 08 / Builder · In progress
    Close the loop.

    Bring the model and drawings into one connected design workspace.

Project documentation snapshot.
Builder integration and drawing conventions remain in development.

An engineering decision
A native process boundary.
A more contained failure.

The Go service invokes the Rust kernel through JSON input and output. Keeping geometry in its own process isolates kernel panics from the API — a system-design choice driven by the behavior of the geometry engine.

The research question

Can a design system explain its decisions in architectural terms, connect each proposed dimension to its evidence, and turn those decisions into executable geometry?

The system

A Go API, PostgreSQL knowledge store, an OpenAI-compatible model endpoint, and a Rust geometry engine. The pipeline connects source passages to decisions, operations, geometry, and derived drawings.

Where it stands

An active research and engineering project. Integrating the builder and completing drawing conventions remain work in progress. Current work uses existing models; custom model training is a future research direction.

Architecture / visual computation

From image to inhabitable form.

An exploration of image-based form generation. Python and OpenCV interpret visual references; Grasshopper and Rhino turn the resulting relationships into a variable canopy.

Python / OpenCVGrasshopperRhino
Inside the design process Image → rules → spatial variations+

Could a two-dimensional reference become a family of inhabitable forms?

This 2022 independent study explored nature-inspired structure in place of a conventional truss. I connected Python and OpenCV image interpretation to GHPython, Grasshopper and Rhino, using parameters to explore multiple canopy configurations.

  1. 01 / Interpret

    Start with a reference.

    Combine biological image references, locate points in three-dimensional space, then interpret their relationships as lines.

  2. 02 / Construct

    Give the lines a surface.

    Form surfaces from the linework and connect their points into a mesh.

  3. 03 / Vary

    Design more than one answer.

    Introduce variability, retain different permutations, and expose those configurations through sliders.

  4. 04 / Refine

    Inspect the result.

    Check for disconnected regions and problematic mesh elements before reviewing the form spatially.

A computational design exploration, not a built project or a validated structural-performance study.

Computational geometry / material expression

Structure in the spaces between.

A mesh-subtraction study that uses Voronoi logic to explore cellular structure, porosity, and light. Built in Grasshopper and Rhino; rendered in Cinema 4D.

The geometric idea Volume → subtraction → skeleton+

What if the empty space defined the structure?

A 2022 independent mesh study exploring an alternative to a conventional truss within a cube. The geometry begins with a volume; a Voronoi-based cellular field removes material and leaves a branching skeleton.

  1. 01 / Define

    Solid and void.

    Use Grasshopper and Rhino to establish the bounding form and the cellular subtraction geometry.

  2. 02 / Subtract

    Keep the spaces between.

    Mesh subtraction reveals an interconnected form. Porosity becomes part of the design language.

  3. 03 / Read

    Study it through light.

    Cinema 4D renders make the surface, openings and vivid red material easier to read.

Computational geometry and material expression. The render explores a structural idea; it does not claim engineering validation.

BIM / production automation

Revit vendor drawing automation

C# / Revit API / APS+

A design change shouldn’t restart days of drawing work.

The bottleneck

Vendor drawings translate a model into information fabrication teams can use. Repeated manual work makes each revision slower to deliver.

What I implemented

C# and the Revit API connect model information to repeatable drawing generation, with APS supporting cloud workflows. I worked with architects and fabrication specialists to connect software rules to production requirements.

Why it matters

The aim is less repetitive preparation and faster responses to changes—freeing time for design decisions while keeping fabrication information consistent.

2023 · Revit, C#, PowerShell, APS and web interfaces. Implementation details shown at a public portfolio level.

Cloud / event-driven engineering

BIM 360 file & folder alerts

ASP.NET / Webhooks / Azure+

Let the change find the person.

The problem

On a shared engineering project, people shouldn’t need to keep reopening folders to discover whether a file has changed.

The system

A management interface lets users configure hooks for BIM 360 / APS file events. An ASP.NET Core backend receives those events and connects them to notification workflows, with email and SMS choices in the interface.

I connected the management UI, APIs and event handling, and deployed the application on Azure. The work made background changes visible without constant manual checking.

A Node.js application uses the Model Properties API to compare two versions. Added, removed and updated elements are visualized alongside the BIM 360 / ACC project hierarchy.

2025 / API investigation

Which data path fits the question?

I compared Data Model, Model Derivative and Data Exchange approaches for element extraction and quantity takeoff. The prototypes cover authentication, hub selection and inspecting element information.

The focus was choosing between targeted element queries, broader model processing and exchanging selected data—not treating every information task as the same API call.

MERN stack · APS · Azure. A record of the project investigation, not a current API pricing or compatibility guide.

The questions I keep following+
“Most of the things I’ve built began this way. Not with a technology. With a question.”

An empty page before the first line. A piece of geometry before it becomes a space. An idea before anyone knows whether it will work. I’ve always been drawn to that moment of possibility.

Experimenting with Grasshopper and Rhino changed how I made things. Change a parameter or a relationship, and the same idea could become something entirely different. Python helped me turn images into geometry. Automation helped me remove repetitive work. Software gave those questions somewhere else to go.

ObjectTracer taught me something about letting an idea into the world. Getting it to work meant following one problem into the next. Then people I’d never met began using it. Something that started on my computer had become useful to someone else.

SEBIRA begins with a different question. Buildings carry decisions, constraints and experience. Can a system move from language to geometry and still explain why? I don’t know how far that idea can go. That’s part of why I’m building it.

That’s what Starman Odyssey means to me: someone who keeps looking toward the stars, willing to follow an idea without knowing exactly where it will lead. There is so much left to learn—and a very long way still to go.
